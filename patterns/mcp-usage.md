# MCP Usage Rule

One rule, shared by every skill that calls an MCP server, so it's stated once instead of re-worded four times:

- **Call MCP tools live, during the skill's own execution.** Never generate code that calls an MCP tool at test runtime - MCP is an authoring/ops-time aid (fetching a story, driving a browser to confirm a locator, posting a PR comment), not something a Playwright test or Page Object ever imports or invokes.
- **If a server isn't connected/authenticated, say so and stop pretending - this is the default, not something each skill opts into.** Covers both "not configured at all" and "configured but missing a local credential/auth grant" (e.g. `testrail`/`figma` before their env vars are set, `atlassian`/`glean_default` before their first auth prompt is completed).
- **Before reacting, decide whether the dependency is *blocking* or *optional* for this specific request** - the two need opposite reactions, so don't apply one blanket "skip gracefully" rule to both:
  - **Optional** = the skill can still produce a meaningfully complete result without this call - e.g. TestRail gap-analysis/mapping is an enrichment on top of a plan that's already grounded in a fetched requirement. Unavailable -> skip gracefully: don't fabricate what it "would have" returned, note what's missing and why, continue with what's actually available.
  - **Blocking** = this call is the *only* way to obtain a required input for the request as given - e.g. a bare Jira ticket ID with no pasted text and neither `atlassian` nor `glean_default` authenticated, or a Figma link with no description and `figma` not authenticated. Unavailable -> **stop, don't degrade.** Never produce a thin/fabricated substitute for the missing input just to have *something* to hand to the next step.
    - **Evaluate blocking across the whole merged request, not per individual source, when more than one source was given for the same feature** (e.g. several Jira IDs, a Jira ID plus a Figma link, a ticket plus extra free text). As long as **at least one** given source resolved to real content, the request isn't blocked - a single failed source among several becomes an explicitly-named gap in the output (e.g. "ABC-1235 couldn't be fetched - neither Atlassian nor Glean authenticated"), not a hard stop. Only stop when **every** given source failed to resolve.
    - **Interactive session (a human is there to answer)**: name every viable alternative server for that content (e.g. "Atlassian or Glean"), then ask the user to either authenticate one of them or supply the content directly (paste it) - and wait for their answer before continuing.
    - **Inside a non-interactive workflow run (no one to ask mid-run)**: return `blocked: true` with a specific `blockReason` naming exactly which server(s) need auth and what the request needed from them - the same escalation mechanism already used for any other pipeline block (see `${CLAUDE_PLUGIN_ROOT}/patterns/workflows-reference.md` §7 "Feature Pipeline" -> "Failure handling"). This requires the calling stage's schema to actually have `blocked`/`blockReason` fields that don't also require the success-only fields (`planPath`, `specFiles`, etc.) - if a schema is missing those, fix the schema, don't route around it by fabricating a result that fits.
- **Tool names aren't hardcoded in any skill.** A server's exact tool names depend on the agent and on what the server exposes at connection time - inspect the live tool list rather than assuming a name matches what's written here.
- **Never write ad-hoc screenshots/snapshots to the repo root.** The Playwright MCP's own tools (`browser_take_screenshot`, `browser_snapshot`) already default to the gitignored `.playwright-mcp/` folder - use that default. If driving the page directly (e.g. `browser_run_code_unsafe`, a raw `page.screenshot()`/`page.locator(...).screenshot()` call) requires an explicit path, point it at `.playwright-mcp/` or `screenshots/` (both gitignored), or delete the file once you're done with it. A stray PNG dropped at repo root during live debugging isn't caught by any test-artifact ignore rule and gets committed by accident.

## Current server status (see `templates/mcp.json`, kept in sync with `${CLAUDE_PLUGIN_ROOT}/docs/MCP-SETUP-GUIDE.md`)

| Server key | Covers | Status                  |
|---|---|-------------------------|
| `playwright` | Browser automation, locator discovery | ✅ Configured           |
| `atlassian` | Jira + Confluence (official Atlassian remote MCP) | ✅ Configured - each developer authorizes via OAuth locally on first use |
| `glean_default` | Enterprise search - also indexes Jira + Confluence (plus Slack, Google Drive, GitHub, etc.) | ✅ Configured - needs `GLEAN_URL` set locally; each developer authorizes locally on first use |
| `testrail` | Test case management (`@bun913/mcp-testrail`) | ✅ Configured - needs `TESTRAIL_URL`/`TESTRAIL_USERNAME`/`TESTRAIL_API_KEY` set locally |
| `figma` | Design specs (`figma-developer-mcp` / Framelink) | ✅ Configured - needs `FIGMA_API_KEY` set locally |

**Atlassian/Glean overlap for Jira & Confluence**: any skill that reads a Jira ticket or Confluence page (`read-ticket`, and anything that composes it) may reach that content through either `atlassian` (`mcp__atlassian__*`, direct/live) or `glean_default` (`mcp__glean_default__search`/`read_document`, indexed search) - use whichever is actually authenticated for the developer running it, rather than failing outright because one specific server isn't. They are not interchangeable for writes: `glean_default` is read-only, so posting a comment, linking a test result, or any other write-back to Jira still requires `atlassian`.

Skills reference this table instead of restating server status inline - if you add/remove a server, update it here once.
