qa-kit is our toolkit for Playwright repos. It plans tests from Jira, Figma and TestRail, writes and heals them, reviews its own work, explores the running app, works out which tests a code change needs, and commits, pushes and opens the pull request only when you tell it to.

One way of working, instead of one per repo

Test automation work repeats the same moves on every ticket. qa-kit turns those moves into shared, reviewable procedures that every team uses the same way.

Planning lives in someone's headThe ticket, the design and the existing coverage are read separately, and the result is rarely written down.
The plan is a Markdown file you review. It merges Jira, Confluence, Figma and TestRail into scenarios with priorities and levels, and skips what is already tested. Open questions are listed, and unclear UI details are marked, never guessed.
Conventions are caught in code reviewNaming, weak assertions and duplicated setup come back as review comments.
Conventions are applied while writing, then checked again. A self-review gate runs before any PR exists, so a human reviewer only judges design and business logic. The target is one review round.
A broken locator is fixed once per testTen failing tests often share one root cause.
Failures are grouped by root cause and healed once. The fix goes into the shared Page Object, then the whole original scope is re-run before anything is reported done.
Automation with no brakes is riskyAn agent that can commit, push and open PRs on its own is hard to trust.
Nothing is committed, pushed or opened unless you ask. Each step needs an explicit flag, and the runner checks that in code. With --commit only files the pipeline produced are staged.
"Fixed" in the ticket is not the same as fixedReproducing a defect means decoding someone else's write-up, then finding out whether a test guards it.
One defect in, a verdict out. It reads the ticket as a defect, reproduces it live, replays once to confirm, and tells you whether a test already covers the flow. If none does, it offers to plan one.
Scripted tests only find what someone expectedReal users click in odd orders and type odd things.
A monkey tester explores the running app on a clock. It tries odd inputs and sequences, proves each finding by replaying it, removes the data it created, and turns confirmed findings into a plan for regression tests.
A red nightly run costs a morningIs it a product bug, a known issue, a changed product, or a flaky test?
Failures are triaged per group, with evidence. It reads the Allure report and its history, retests only what failed, cross-checks the Jira issues you give it, and advises. It drafts tickets and never files them.
CI runs everything for a one-line changeA full suite on every small change is slow and noisy.
The change decides what runs. It reads your checkout, a branch, pull requests or the last few days, and a tested script picks the narrowest safe run. Unsure means the full suite. Nothing changed means nothing runs.

From ticket to pull request in seven stages

You can run one stage at a time, or chain them. Three of the stages wait for you: reviewing the plan, committing, and pushing or opening a PR. Pick a stage to see what it does.

Then let a monkey try to break it

Scripted tests check what someone thought of. The monkey tester explores one area of the running app like a curious, slightly hostile tester, and every finding comes with proof.

  1. Understand firstBefore it acts on a page it reads the conventions, the plan scenarios and the existing tests, and takes one read-only look at the screen. It keeps a short card per page and reuses it while nothing has changed.
  2. Explore on a clock5 minutes by default, 30 at most, with an optional focus in plain words. It tries edge inputs, odd sequences and the gaps the existing tests do not script.
  3. Prove every findingA finding needs a named reason and evidence, then it is replayed once. It is reported as reproduced 2/2, flaky, or listed as unconfirmed and never counted as a defect.
  4. Clean up and reportIt removes only the data it created, then writes a report with the same seven sections every time, and a plan for the findings that reproduced.

What counts as a finding

  • Hard evidence: an uncaught script error, a failing first-party request, a blank or stuck page, a dead end.
  • Softer, labelled as advice: it contradicts a plan scenario, the app disagrees with itself, an error nobody could understand, a control that does not do what its label says.
  • Severity 1 to 4: crash or data loss, broken function, degraded, cosmetic.

Fenced in

  • Refuses a production-looking host, with no override.
  • Writes only under qa-kit-artifacts/monkey/. Never touches git, tracked files or .env.
  • Never touches billing, invitations, outbound messages, account settings or other origins.
  • Creates only data named with its own run prefix, at most 25 per run, and deletes one verified item at a time from its own ledger.
  • Anything that looks protected (NOT, SOURCE, SEED, TEMPLATE, KEEP, fixtures the tests use) is read-only, and listed as left alone.

What you get

  • monkey-report.md with Run, Coverage, Findings, Unconfirmed, Data, Environment and Not explored.
  • findings-plan.md with only the findings that reproduced 2/2, in the normal plan format.
  • Running feature-implement on that plan turns them into regression tests. That step stays a human decision.
  • Several areas at once with feature-monkey, 2 at a time by default. They share one app and one test account.
# one area, in your conversation
/qa-kit:monkey-test checkout --minutes=5 --guidance="odd quantities and coupons"
# several areas, in parallel, creating no data
/qa-kit:feature-monkey checkout "order history" --read-only
# confirmed findings to regression tests
/qa-kit:feature-implement qa-kit-artifacts/monkey/<slug>/findings-plan.md

Start from the code that changed

Plans start from a ticket. This starts from a diff: what do my changes affect, which tests should CI run, and what is not covered yet. It is read-only, and when it is unsure it answers the full suite.

Where it reads from

  • Your checkout against the default branch: committed, staged, unstaged and new files.
  • Another base, a committed ref, a pull request or a range.
  • The last N days of commits.
  • Pull requests of one or more separate GitHub app repos, read together as one change set.

Facts by the agent, the decision by code

  • The agent records what changed, what kind of change each file is, and which tests it affects.
  • A tested script decides how much to run, crossing that with your optional mapping file.
  • Both sources agree: high confidence. One source: medium. They disagree: low.

Never narrower than the evidence

  • The full suite for a global change, shared application code, a change no test was found for, low confidence, or a change set it could not read in full.
  • Nothing changed, or documentation only: run nothing.
  • A narrowed run also adds the smoke specs of the affected features.
# which tests does my checkout need?
/qa-kit:feature-select --base=origin/main
# the last 7 days: gaps planned, affected tests run once
/qa-kit:feature-diff --since=7 --run-affected
# a pull request of the app repo, with plans for the gaps
/qa-kit:feature-select --repo=org/app 456 --plan

Results land in qa-kit-artifacts/changes/ as Markdown for people and JSON for scripts, including a one-line argument list for the test runner. The CI wiring is not built yet: a consumer treats a non-zero exit, a blocked entry or a missing selection as the full suite.

Twenty skills, nine agents

A skill is one procedure. An agent is a role with specific tool permissions that runs one skill at a time. Open any row for the detail and an example command.

agent-planner

Reads requirements and produces the plan. Read-only toward git.

runs plan-tests

agent-writer

Writes specs and Page Objects that follow the repo's conventions.

runs write-tests

agent-executor

Runs the suite, classifies failures and heals them. Has no Write tool, so a new file becomes a blocked result for a human.

runs heal-tests or execute-tests

agent-reviewer

Reviews, checks the tests against the plan, and applies fixes on its own branch. Never touches git.

runs review-tests, verify-coverage, apply-review-fixes

agent-deliverer

Commits what already passed review, and pushes or opens the PR only when told. Has no edit tool.

runs commit-and-push, create-pr

agent-triager

Works after a run, on one failed Allure report. Jira access is read-only, and it edits tests only with --heal.

runs triage-failure

agent-defect-retester

Starts from one Jira defect and reproduces it live. Jira access is read-only, it has no Edit tool, and it never plans or implements without being asked.

runs retest-defect

agent-change-analyst

Records the facts about a set of changes: what changed, what kind of change it is, which tests it affects. Read-only, with no Edit tool and no browser. A script decides how much to run, not the agent.

runs analyze-changes, select-tests

agent-monkey

Explores one area of the running app within a time budget. Writes only under qa-kit-artifacts/monkey/, has no Edit tool, and never uses the unsafe run-code browser tool.

runs monkey-test

One feature or several

Pick one track per feature. The plan file is the hand-off between them.

Manual trackRun the skills one at a time in your own checkout. Most control.
Pipeline trackfeature-plan, feature-implement and feature-deliver. Several features run in parallel, up to 3 by default, each in its own worktree and branch. Implement stops after review, and feature-deliver commits when you are ready. feature-monkey explores several areas at once. feature-select and feature-diff start from a code change instead of a ticket.

Built so that you can trust it with your repo

These are rules the kit follows every time, and where it can, rules it checks in code instead of asking the model to remember.

Read-only where it matters

Planning, coverage checks and change analysis write only to qa-kit-artifacts/ and never touch git. Triage and defect retests never create, edit or comment on a Jira issue.

No commit, push or PR, unless asked

--commit, --push and --pr are a ladder, each implying the one before. The pipeline never decides this itself.

Runner: deny rules plus post-run checks, exit code 3

Your work stays yours

With --commit, only files the pipeline produced are staged, one by path, and never a file you had already changed. No git add -A, no --no-verify, no force-push, no commit on the default branch.

Delivering says what it took

feature-deliver is the request to deliver, so it commits every change git shows, your hand edits included. It lists what it added beyond the pipeline's files, and a secret file stops it. Check the list before --push.

No secrets in the repo

Tokens and URLs live in your shell environment. Jira and Glean use browser sign-in. No model, provider or API-key settings are ever written.

Setup changes are reviewed

init shows a plan with diffs first. Existing files change only when you accept them, one at a time. Conflicts are never written into your file, and init never commits.

Your conventions win

.qa-kit/project/conventions.md overrides the kit's defaults for every skill. Updates merge the kit's new rows into it through a reviewed three-way merge and never overwrite your edits.

Monkey runs are fenced

No production-looking host, with no override. They write only under qa-kit-artifacts/monkey/ and never touch git, tracked files or .env.

Runner: no changes outside the folder, .env unchanged, exit code 3

Only its own data

It creates only data named with its run prefix and deletes only entries in its own ledger, one verified item at a time. Anything protected-looking is read-only and listed as left alone.

Two known gaps, stated plainly. On OpenCode, outside the runner, nothing in the kit blocks git push or gh pr create; the skills' own confirmation prompts are the guard there, while Claude Code's repo permissions keep both as prompts. And defect retests have no pipeline entry, so the runner cannot check them afterwards: their limits rest on the skill's rules and the agent's tool list.

Set up a repo once, then everyone just works

One person runs init per repo and opens a PR with what it wrote. Everyone else installs the kit once per machine and pulls.

  1. Run /qa-kit:initIt detects your agents, package manager, test folder and default branch, and asks only about the rest.
  2. Read the planNothing is written yet. Every file gets a status and a diff.
  3. Accept what you wantFile by file. Anything it cannot settle automatically becomes a review copy.
  4. Fill in your conventionsPre-filled from the repo. Your file, and it overrides the kit's defaults.
  5. Commit and open the PR yourselfThe report lists exactly which files to stage.
What lands in your repo

AGENTS.md with the standards, a one-line CLAUDE.md import, .claude/settings.json with permissions, .mcp.json and opencode.json from one server list, and .qa-kit/ with your conventions and a manifest.

Your conventions file also gets a Monkey rules section: hosts to never run against, known console noise and protected data. init pre-fills the production hosts it can see in non-secret config.

An optional change-mapping.md (app paths per feature, global and ignorable paths, the full-run threshold) is created once and never auto-updated.

Run-time output goes to qa-kit-artifacts/, which ignores itself and can never be committed.

Updates are a reviewed three-way merge

When a new kit version arrives, init compares what the kit wrote last time, what it renders now, and your file. Your edits stay on top of the new content.

fast-forwardmergeconflictunknown-basekeptunchanged

The previous version is not stored in your repo. It is rebuilt from the git tag that wrote each file, and if that fails nothing is overwritten. Some releases, such as 0.10.0, ask you to re-run init so the command table in AGENTS.md and the new rows in your conventions file arrive as reviewed merges, including new read-only permissions for change analysis. A clash on the same lines becomes a review copy, never an overwrite.

Repos that are not only automation

init --path=automation puts the whole install in one subfolder. Developers elsewhere in the repo get no instructions file, no MCP servers and no plugin offer. People start the agent in that folder.

Planning without any repo

read-ticket, plan-tests and feature-plan need no repo. Register the tools once with /qa-kit:init --user, then run from any folder.

Try it on your next ticket

Install the kit once per machine. Then plan a ticket in any folder, or set up your repo with init. Not sure where to start? Type /qa-kit:help for one screen with the recommended path, every flow and skill, and examples.

Where it stands

  • Version 0.10.0, for Playwright repos, on Claude Code and OpenCode.
  • Permission rules for OpenCode are not generated yet.
  • Monkey testing: traces, video and generated repro specs are not produced yet.
  • Change-driven testing: the CI wiring is not built yet, and it has not been checked on real repositories.
  • Defect retesting: how much of a ticket's screenshots and attachments the Jira and Glean servers return is not checked yet.
  • Atlassian is on the v1 endpoint for now; move to v2 before 2027-03-01.
