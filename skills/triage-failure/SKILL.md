# Triage Failure

**Purpose**: Turn "the nightly run failed" into advice per failure group: what it most likely is, why, since when it has been failing, whether it is already filed, and what to do next - confirmed by re-running only what failed. The verdicts are advice from evidence, never facts.

**Scope**: small on purpose. It works on the failed tests of one report, after a run (CI, nightly, dispatch). Running and healing a whole set of specs while writing tests is `agent-executor`'s job, not this skill's.

**Project overrides**: if the repo has `.qa-kit/project/conventions.md`, read it first: its *Commands* table replaces the `npx playwright test` examples below, and a ticket-link convention (an annotation or tag that ties a test to a Jira key), if it names one, is used in Step 4.

**Hard limits** (they hold whoever invokes this skill, now or from CI later):
- It **never creates, edits, transitions or comments on a Jira issue**, even if the request says "and file it". It drafts files; a human files them. The only Atlassian tools it may use are the read-only `get`, `search` and `lookup` ones, and from Glean only `search` and `read_document`.
- It **edits test code only with `--heal`**, only for `test-fix` groups, and never in a spec file that already has uncommitted changes (Step 8). It never edits config, support code or anything else.
- It **never changes git state**: no add, commit, stash, checkout or push. Reading `git status` is the only git use.
- It **never asks for a token, cookie or password**, and never writes one into a file. Anything secret-looking in an error or trace is removed from the drafts.
- It **asks no questions**. A missing or unreachable input ends the run `blocked` with the exact reason and what the person can do, so the same procedure can run unattended.

## How this skill is invoked

- **On demand, by a human**: `/qa-kit:triage-failure https://<pages-host>/<environment>/<run-number>/` or `/qa-kit:triage-failure ./allure-results`. Flags:

| Flag | Meaning |
|---|---|
| `--known=ABC-12,ABC-40` or `--known="<JQL>"` | Jira issues (bugs, stories, epics) or one JQL to cross-check the failures against (Step 4). A value whose comma-separated parts are all keys or Jira URLs is a key list; anything else is one JQL |
| `--heal` | After classifying, heal the `test-fix` groups (Step 8). Off by default |
| `--triage-only` | The default, accepted for clarity |
| `--no-retest` | Classify from the report alone; nothing is run and every verdict is capped at low confidence |
| `--from=<triage.json>` | Load an earlier result instead of fetching, retesting and classifying again (see "Continuing from a result") |
| `--groups=g1,g2` | With `--from`: act only on these groups |

- **From `agent-triager`**: the same procedure, run non-interactively (`${CLAUDE_PLUGIN_ROOT}/agents/agent-triager.md`).
- **Later from CI**: not wired up today. Inputs are arguments only and the outputs are files, so a CI step or a runner entry can call it. CI should run it triage-only.

## Workflow

### Step 1: Get the failed tests and their history

Accept one of three inputs and extract, for every `failed` or `broken` test: name, full name, status, message, trace, labels (suite, feature, tags), steps if present, the environment the run used, and the test's earlier results (Step 3).

**A. A report URL** (an Allure 2 report generated by `allure generate`). Normalise it first: drop the `#...` fragment and a trailing `index.html`, keep the folder ending in `/`. Then, with `curl -fsSL` through Bash (no credentials):
- `<base>widgets/summary.json` for the counts and `<base>widgets/environment.json` for the environment;
- `<base>data/suites.json` for the tree - the leaves with a failed or broken status carry a `uid`;
- `<base>data/test-cases/<uid>.json` for each of those, and `<base>history/history.json` for the history of all tests.

If a response is not JSON (a login page, a redirect, 401/403/404), the site is private or the layout differs: go to B or C.

**B. A local folder**: a generated report (it has `data/test-cases/`) or an `allure-results` folder (`*-result.json` files with `status`, `name`, `fullName`, `statusDetails`, `labels`, `steps`, and a `history/` folder if the run copied it in). Read it directly.

**C. Fall back to the run's artifacts** when A fails and the URL path ends in `<environment>/<run-number>/` (the layout `actions/allure-archive` publishes): with the user's own `gh` login, find the repository from `git remote get-url origin`, locate the workflow run with that run number (`gh run list --limit 200 --json databaseId,number`), and download the results artifact (`gh run download <id> --pattern 'allure-results-*' --dir qa-kit-artifacts/triage/<slug>/results`). Then continue as B. Artifacts expire (30 days by default).

If nothing works, end `blocked` with: which input was tried, why it failed, and what to do (pass a local `allure-results` folder, or download the `allure-results-*` artifact of that run). A single-file report (one `index.html` with the data embedded) cannot be read: say so and ask for the results folder in the blockReason.

Only the Allure 2 layout is read. If the structure above is absent, report that instead of guessing.

### Step 2: Map each failure to a spec and group

For each failed test find the spec file and the test in the repo: take the file from the full name or the suite labels, check it exists with `Glob`, and if it cannot be derived, `Grep` for the test title under the test directory. A test that cannot be located is `unverified` with the reason - it cannot be retested or healed.

**Group failures that share a root cause** before anything else, as `execute-tests` does: the same error with a stack trace inside one `beforeAll`/`beforeEach`, or several failures pointing at the same Page Object method or locator, are one group. Triage groups, not individual tests. Number the groups `g1`, `g2`, ... in the order they will be reported; the ids stay the same in every output so a follow-up can name them.

### Step 3: Failure history

From the report's own history (`history/history.json`; the per-test `data/test-cases/<uid>.json` `extra.history` items with status and message, newest first; or the `history/` folder inside an allure-results folder), compute per test and then per group over the available window (Allure keeps about 20 runs; retention may shorten it):

- **pattern**: `new` (passed in every earlier run), `constant` (failed in every run of the streak), `intermittent` (mixed), `unknown` (no history);
- **consecutive failures**, **first failed in**, **last passed in**, **failures in window** as `k of n`;
- **same error as before**: whether the earlier failures carry the same error message (separates "one bug for six nights" from "six different problems").

Name the earlier runs with a run number and date when they can be known: from the item's report link, or where `<environment>/<run number>/run-summary.json` exists next to the report (the archive layout), from that file. Otherwise use the date alone. If there is no history (a new test, a results folder without `history/`, a single-file report), say "history not available" and continue; never reconstruct it from guesses.

### Step 4: Known issues (`--known`)

Optional and read-only (`${CLAUDE_PLUGIN_ROOT}/patterns/mcp-usage.md`): if `--known` was not given, skip to Step 5 and rely on the duplicate search in Step 9.

- Read each key or URL with the read-only Atlassian tools, falling back to Glean `search` / `read_document` the way `read-ticket` does. Never hardcode tool names: inspect the live tool list. Expand an **epic** to its children with a read-only search, run a **JQL** as a search, and cap the total at 50 issues (say so if more matched).
- Record per issue: key, type, summary, status and whether it is open or resolved (status category), resolution date, and the trimmed description and comments.
- If Jira cannot be read, say "known-issues check skipped: <why>" in the report and carry on. Never block on it.

**Match each failure group to the issues**:
- **Strong**: the test links the key (an annotation, tag or title, using the convention in `conventions.md` if it names one, otherwise any listed key found in the test's title, annotations or nearby comments), or the issue text contains the test title, the spec file path or the distinctive first line of the error.
- **Weak**: only shared keywords between the issue summary and the error or test title. Listed as "Possible duplicates"; it never changes a verdict and never suppresses a draft.
- Only bugs can match strongly. Stories and epics supply context ("ABC-9, In Progress, changes this screen") for `deviation` and `product-gap` and never suppress anything.

**Cross-check with the history**: compare the group's first failure with the resolution dates of the listed stories, epics and bugs. A related item resolved shortly before the first failure is cited as the likely cause. A failure that began with no related change is called unexplained.

### Step 5: Scope the retest and run it

Run only what failed, plus everything the failed tests need to be meaningful:

- **Project dependencies**: read `playwright.config.ts`, find the `project` each failed spec belongs to (`testMatch`/`testDir`) and run with `--project=<name>`. Playwright then runs that project's `dependencies` (setup, login) first. Never pass `--no-deps`.
- **Serial blocks**: a failed test inside `test.describe.configure({ mode: 'serial' })` (or `test.describe.serial`) is retested with its whole `describe`, because earlier tests in it create the state it needs.
- **Gating hooks**: a group failing at one `beforeAll`/`beforeEach` is retested through any one test of the group plus the hook, not per test.
- **Fixtures** come along automatically with the spec file.

Build one command per project, for example `npx playwright test <spec files> --project=<name> --grep "<title 1>|<title 2>"`. With more than 25 failed tests, retest per spec file instead of per title. Run through the `execute-tests` skill (report-only, never `--heal`) so the project's commands, headless rule and failure grouping apply: headless when the prompt says so or `CI=true`, otherwise its normal default. Run each scope **once**.

The retest runs on the machine and environment configured here, which may not be the environment of the report: record both and say so when they differ, because a pass here then proves less. With `--no-retest`, skip this step.

### Step 6: Live check (locator-type failures only)

For a group that fails again with a locator or timeout error, tell "moved" from "gone" before choosing between `test-fix` and `product-gap`: invoke `discover-locator` (read-only) for the element the test targets. It found an equivalent element: the page changed shape and the test is out of date. It found nothing: the capability may be missing or removed. Skip this step when the app is not reachable and say so; the verdict is then capped at medium confidence.

### Step 7: Advise

Give every group one verdict from this table, a confidence (**high**, **medium**, **low**), the reasons, the main alternative that was ruled out, and next actions. Use the error types of `execute-tests` (locator, timing, state, API, assertion) on the original error, then weigh the retest, the history, the live check, the known issues and the plan file under `qa-kit-artifacts/` if the test came from one.

| Verdict | Meaning | Typical evidence | Next action offered |
|---|---|---|---|
| **product-bug** | The product is wrong; the test is right | Fails again on retest; the value or response contradicts the requirement or the old behavior; no related change found | Ticket draft (Step 9) |
| **known-issue** | Already filed and still open | Strong match to an open bug and it fails again | Nothing to file; suggested comment text only (the report text, never posted) |
| **deviation** | The product changed, probably on purpose, and the test expectation is outdated | Assertion mismatch plus a related story or epic that explains the change (resolved or in progress), or the plan says the new value | Confirm with the story, then update the expectation by hand or via `write-tests`. Never healed: healing never changes an expected value |
| **product-gap** | The capability the test needs does not exist (yet) | No equivalent element or route at all (live check finds nothing, API 404 on a route the test assumes), the related story is open or in progress, or a flag is off | Link the story; mark `test.fixme` with the ticket, or wait |
| **test-fix** | The test needs tuning: locator, timing, state or data | A locator, timing or state error; the element exists but moved or was renamed; fails again the same way | `--heal`, or `/qa-kit:heal-tests <spec>` |
| **flaky** | Intermittent | Passed on retest | Note the shared cause if several tests share one; a stability follow-up is the person's call |
| **environment** | Infrastructure, service, data or config | 5xx or network errors across many unrelated tests, setup or login failing | Check service and environment health first; no ticket |
| **unverified** | Could not be decided | Not retested (`--no-retest`, setup failed, spec not found) or the evidence is mixed | Say exactly what is missing |

**How the evidence moves a verdict**:
- A strong match to a **resolved** bug that fails again stays `product-bug`, flagged "regression candidate: ABC-12 resolved on <date>"; its draft links it as related.
- An **open** bug whose test passes on retest becomes `flaky` with "ABC-12 may be fixed or intermittent: worth checking". Known-issue failures are still retested: it is cheap and the only way to notice a fix.
- A **new** failure (passed in every earlier run) is listed first. A related story resolved just before it points to `deviation` or a regression. A **constant** failure with the same error and no known issue is flagged "long-standing, never reported" and is the strongest `product-bug` or `test-fix` signal.
- An **intermittent** history plus a pass on retest makes `flaky` high confidence; an intermittent history that fails on retest stays medium.
- When the evidence is mixed take the cautious verdict, lower the confidence, and say what would settle it. Never report `product-bug` for something that passed on retest.

### Step 8: Heal (only with `--heal`)

Skip this step unless `--heal` was given (or `--from` named a heal). Only `test-fix` groups are healed; every other verdict is left alone.

- **Safeguard**: before healing a group, run `git status --porcelain -- <its spec files>`. A file with uncommitted changes is not touched and its group is marked `blocked` with the file name, so a person's unfinished edit is never changed under them.
- Invoke `heal-tests` with the grouped failure list of that group (it accepts one; see its Step 0). When it would ask the user, record the group as `needs-human` with the question it would have asked. Never ask.
- Re-run the healed scope once through `execute-tests`. A group that still fails stays `test-fix`, marked "heal did not resolve".
- Healed files stay uncommitted. Name them in the report and give `/qa-kit:feature-deliver` as the next step (it reviews and commits them). Nothing is committed or pushed here.

### Step 9: Draft tickets for probable product bugs

One draft per `product-bug` group, never per test, and none for `known-issue`. Before writing it, if the read-only Atlassian tools are available, search for an existing ticket with the failing behavior's key words and note any likely match under "Possible duplicates"; if they are not available, say so and continue.

Write `qa-kit-artifacts/triage/<slug>/ticket-<n>-<short-title>.md`:

```
Project: <PROJECT>            (the project key of the --known issues if they share one, otherwise leave the placeholder)
Issue type: Bug
Summary: <one line: behavior and where, no test names>
Environment: <environment and URL the failing run used>
Description:
  What was expected, what happened, the steps (from the test's steps, in plain words).
Evidence:
  Error message (trimmed), the retest result, the failure history ("first failed in run 407, 6 consecutive runs, same error"), the report URL, run number, date.
Affected tests: <list, grouped>
Possible duplicates: <ticket keys found, or "none found", or "not checked: no Jira read access">
Related: <regression of / related to ABC-12, when a resolved bug matched>
Suggested labels: <area/feature tag from the tests>
```

State in the conversation that nothing was filed and where the drafts are.

### Step 10: Write the outputs and show the report

Create `qa-kit-artifacts/triage/<slug>/` (the folder ignores itself; `<slug>` is `<environment>-<run number>` from the URL, or the folder name plus the date). Write `triage.json` and `triage-report.md` (same content as the screen report), then end the conversation turn with the **screen report** below, so the person can read it and keep working in the same session.

**Screen report** (this order, plain text):

```
Triage: <source>   report env: <x>   retest env: <y>   retested: yes   known issues: 8 read
Found 12 failed tests in 5 groups: 1 product-bug, 1 known-issue, 1 deviation, 1 test-fix, 1 flaky

g1  product-bug  (high)   3 tests   <spec files>
    What:    <one line, the failure in plain words>
    Why:     <the 2-3 pieces of evidence behind the verdict>
    History: failing 6 runs in a row since run 407 (2026-11-09), same error; ABC-9 resolved 2026-11-08
    Not:     <the alternative ruled out, and what would settle it when confidence is not high>
    Next:    draft written to <path>
g2  ...

Next actions (copy-pasteable, safest first)
  1. File g1: <draft path>
  2. Heal g4: /qa-kit:triage-failure --from <triage.json> --heal --groups=g4
Files: <triage.json>  <triage-report.md>  <ticket drafts>
```

A `new` failure is listed first, then by confidence. Group ids are stable, so a follow-up in the same conversation can say "heal g4" or "draft a ticket for g2" and the context is already there.

**`triage.json`** (what a script or a later CI step reads):

```json
{
  "source": "<url or path>",
  "environment": { "report": "<name>", "retest": "<name>" },
  "retested": true,
  "knownChecked": true,
  "counts": { "failed": 12, "groups": 5, "product-bug": 1, "known-issue": 1, "deviation": 1, "product-gap": 0, "test-fix": 1, "flaky": 1, "environment": 0, "unverified": 0 },
  "groups": [
    {
      "id": "g1",
      "verdict": "product-bug",
      "confidence": "high",
      "summary": "<one line>",
      "why": ["<evidence>"],
      "alternatives": ["<ruled out, and what would settle it>"],
      "tests": [{ "name": "<test title>", "file": "<spec path>" }],
      "evidence": { "originalError": "<short>", "retest": "failed", "liveCheck": "not run", "known": [{ "key": "ABC-12", "status": "open", "strength": "strong", "relation": "same failure" }], "related": ["ABC-9"] },
      "history": { "window": 20, "failedInWindow": 6, "consecutiveFailures": 6, "firstFailed": { "run": 407, "date": "2026-11-09" }, "lastPassed": { "run": 406, "date": "2026-11-08" }, "sameErrorAsBefore": true, "pattern": "constant" },
      "nextActions": [{ "action": "file ticket", "command": "qa-kit-artifacts/triage/<slug>/ticket-1-<short-title>.md" }],
      "ticketDraft": "qa-kit-artifacts/triage/<slug>/ticket-1-<short-title>.md",
      "heal": { "attempted": false, "result": null, "files": [] }
    }
  ],
  "blocked": false,
  "blockReason": null
}
```

A blocked run still writes `triage.json` with `blocked: true` and the reason, and the screen report says so first.

## Continuing from a result (`--from`)

`/qa-kit:triage-failure --from=qa-kit-artifacts/triage/<slug>/triage.json --heal --groups=g4` loads an earlier result, skips Steps 1 to 7, and applies only the requested action to the named groups (all `test-fix` groups when `--groups` is absent): Step 8 for `--heal`, Step 9 for a missing draft. This is the CI-then-local flow: CI runs triage-only and keeps `triage.json`; a person later heals locally. A stale result is caught because `heal-tests` re-runs the scope itself and the Step 8 safeguard reads the current `git status`. Write the updated `heal` fields back into `triage.json` and show the screen report again.

---

## Quality criteria

1. Every verdict names its evidence and its confidence, and a low-confidence one says what would settle it.
2. Retests are scoped (failed tests, their project dependencies, their serial block), never the whole suite.
3. A draft ticket is something a person can file without reopening the report.
4. Uncertain means `unverified` or the cautious verdict, never a confident guess.
5. History and known issues enrich a verdict; when they are unavailable the run says so and goes on.

**Note**: This skill classifies, drafts and, only on request, heals `test-fix` groups. Use `heal-tests` directly to fix a specific spec, `execute-tests` to run tests, `write-tests` for new coverage or a changed expectation, and `feature-deliver` to commit what was healed. Filing the Jira ticket is always a human step.
