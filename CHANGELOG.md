# Changelog

Versions follow semver. Consumers only receive an update when `version` in `.claude-plugin/plugin.json` changes, so bump it in every release commit and tag it with the plain version, for example `0.1.0` (no `plugin-v` prefix; `v1`-style tags are reserved for the GitHub Actions).

## 0.8.0 - moved to `ngavishtech/qa-kit`, public and agnostic, `GLEAN_URL`

**Breaking for existing installs.** The marketplace is now `ngavish-qa` (repository `ngavishtech/qa-kit`), so the plugin id is `qa-kit@ngavish-qa`. Uninstall the old one and install the new one (`claude plugin uninstall qa-kit@<old marketplace>`, `claude plugin marketplace add ngavishtech/qa-kit`, `claude plugin install qa-kit@ngavish-qa --scope user`); having both installed duplicates every `qa-kit:` skill. Repos set up by an earlier `init` still name the old marketplace and kit URL in `.claude/settings.json` and `AGENTS.md`: re-run `init` with `--kit-url https://github.com/ngavishtech/qa-kit`.

- **The Glean MCP URL is no longer baked into `templates/mcp.json`.** It is `${GLEAN_URL}`, like `FIGMA_API_KEY` and `TESTRAIL_*`: export it in the shell that starts the agent (ask your Glean admin for the MCP URL). Without it Claude Code still lists `glean_default`, warns about the missing variable in `/mcp` and the server cannot connect; Atlassian is unaffected. To pick the change up in a repo, re-run `init` (a reviewed merge; check that `glean_default` in `.mcp.json` now reads `${GLEAN_URL}`; this merge was not tested against a repo that has the old URL). `init --user` never changes a server that already exists, so if you registered `glean_default` at user level before, remove it (`claude mcp remove glean_default --scope user`) and run `/qa-kit:init --user` again.
- **OpenCode conversion now maps `${VAR}` in a server `url`** to `{env:VAR}` (it only did so for `env` values before), and the user-level MCP setup lists `GLEAN_URL` under "Export before use".
- The kit no longer describes itself as internal: employer, product and tenant names, the "internal only" audience statement and the private-repository instructions were removed from the README, the docs and the project guide. Docs that listed the Glean host or said the packages are pinned now match the code (`GLEAN_URL`, `@latest`).

## 0.7.0 - opt-in delivery, `test-deliverer`, `verify-coverage`, `triage-failure`, `test-triager` and the monkey tester (`monkey-test`, `test-monkey`, `feature-monkey`)

**Behavior change.** Before, every `feature-implement` run ended with a local commit. Now it stops after Review and commits only when asked. Scripts or habits that relied on the automatic commit need `--commit` (or `--push` / `--pr`, which imply it), or a `/qa-kit:feature-deliver` afterwards.

Re-run `init` after updating: the `AGENTS.md` command table mentions the new flag, and `.qa-kit/project/conventions.md` gets the kit's new rows, so both arrive as reviewed merges. The `AGENTS.md` table also gets the monkey tester row and `conventions.md` a `## Monkey rules` section.

- **`--commit` (new), `--push`, `--pr` are a ladder.** `--push` implies `--commit` and `--pr` implies `--push`. With none of them the Deliver stage is skipped: the tests stay uncommitted in your checkout (one plan) or in each plan's worktree (several), `report[].committed` is `false`, and the run log says where they are.
- **`/qa-kit:feature-deliver` is the "deliver on demand" step.** It reviews (with the confirming re-review), then always commits, because running it is the request to deliver; `--push` and `--pr` add the rest. With no target it picks up the previous `feature-implement` run, or the branch you are on. `--commit` is accepted there but changes nothing.
- **Fix:** `feature-deliver`'s Deliver step now carries `baselineChanges`, so files that were already modified before the implement run are never staged by a later deliver (the `feature-implement` prompt already did this).
- **New agent `test-deliverer`** (tools: `Bash, Read, Glob, Grep, Skill`; no edit tool) owns the Deliver stage of both workflows. `test-reviewer` now only reviews and never touches git. Side effect: if `create-pr`'s own self-review gate still finds a Blocking or Should-fix finding, the Deliver stage reports `blocked` instead of fixing it; run `/qa-kit:feature-deliver` and deliver again.
- **Runner safety:** the Claude adapter denies `git commit` unless the run was authorized to commit, and the post-run check exits `3` when a run without `--commit` reports a commit or moves a branch that already existed. For a branch created during the run, only the agent's own report is checked.
- **New skill `verify-coverage` (read-only)** answers "is this already tested, and do the tests match the plan?" with `file:line` evidence, in two modes:
  - *Plan mode*, called by `plan-tests` Step 3 and Update Mode (so `feature-plan` too): every candidate scenario is marked `duplicate`, `partial` or `new` against the repo's specs and the TestRail cases already fetched. A duplicate is removed from Test Scenarios only with a row in Existing Coverage; a partial names the test it extends. See "Coverage cross-check" in `patterns/test-plan-format.md`.
  - *Implementation mode*, called by `test-reviewer` in the `feature-implement` Review stage (the prompt now names the plan and the `--level`): maps each plan scenario to a written test and reports missing (Blocking, ends the stage `blocked`), weak (Should fix), duplicate of an existing test (Should fix) and extra tests. `report[].coverageGaps` and the runner summary carry the missing and weak ones. `feature-deliver` has no plan, so it does not run it.
- **New skill `triage-failure` and agent `test-triager`**: `/qa-kit:triage-failure <Allure report URL | report folder | allure-results folder> [--known=<keys or JQL>] [--heal] [--no-retest]`, or `--from=<triage.json> [--groups=g1,g2]` to continue from an earlier result. After a run (CI, nightly, dispatch) it takes the failed tests of one report, retests only them plus their Playwright project dependencies and serial blocks, and **advises per failure group** with a confidence, the reasons, the alternative ruled out and next actions:
  - verdicts: `product-bug`, `known-issue`, `deviation` (the product changed on purpose, the expectation is outdated), `product-gap` (the capability is not there yet), `test-fix` (the test needs tuning), `flaky`, `environment`, `unverified`. A read-only live check (`discover-locator`) tells a moved element from a missing one.
  - **failure history**: pattern (new, constant, intermittent), consecutive failures, "failing since run N (date)", same error as before, read from the report's own Allure history; a failure that began right after a related story was resolved says so.
  - **`--known`**: Jira keys (bugs, stories, epics) or one JQL, read with the read-only Atlassian tools (Glean as fallback). A strong match to an open bug is a `known-issue` and no second ticket is drafted; a resolved bug that fails again is a regression candidate; an open bug whose test passes is noted as possibly fixed.
  - **output**: the final message is a screen report (one block per group, stable ids `g1`, `g2`, copy-pasteable next actions) so the session can continue from it; `qa-kit-artifacts/triage/<slug>/` holds `triage-report.md`, `triage.json` and a `ticket-<n>-*.md` draft per probable product bug.
  - **`--heal`** (off by default) heals only `test-fix` groups through `heal-tests`, never in a spec file that already has uncommitted changes (that group is `blocked`), re-runs the healed scope once and leaves the files uncommitted for `/qa-kit:feature-deliver`. CI should run triage-only and heal locally with `--from`.
  - **limits**: never creates, edits, transitions or comments on a Jira issue (read-only Atlassian `get`/`search`/`lookup`, Glean `search`/`read_document`), never changes git state, asks no questions, never asks for a token. A private Pages site falls back to the run's `allure-results-*` artifact through the user's own `gh` login. Only the Allure 2 file layout is read, and neither the layout nor the history fields have been checked against a real report yet (Pilot checklist item 27).
  - `test-triager` has an explicit tool list (read-only Jira, the same Playwright tools as `test-executor`, no `browser_run_code_unsafe`); `test-executor` is unchanged. `templates/project/conventions.md` gains an optional "Ticket link in tests" line (new installs only).
- **Hardening of opt-in delivery** (found in an audit of the changes above):
  - **Uncommitted work now carries across runs.** Every `feature-implement` report entry records `ownedFiles`: each path the pipeline created or changed on that branch (spec files and support code, healed files, review fixes), carried forward. The next run on the same plan gets them as `priorOwned` (the runner reads `latest/`, Claude Code the conversation's report entry), subtracts them from its baseline and continues from them. Before, `--level=smoke` then `--level=sanity` without committing in between made the second run take the first run's specs for the user's own edits, so Deliver left them out.
  - **Deliver stages the pipeline's files by name** (`ownedFiles`, one `git add -- <path>` each) and Review reviews them and never edits a baseline path. `feature-deliver` targets carry `ownedFiles`. With no recorded run (a fresh Claude session, the current-checkout fallback) behavior is as before and the report's `scope` says "no recorded run".
  - **`feature-deliver` delivers everything you changed.** Running it is the request to deliver: it commits every change git shows in the project folder (modified, deleted, renamed and staged files, and new files that are not ignored). That is the pipeline's files plus anything you changed or added by hand after the implement run to close a gap, a file you had already modified before the implement run, and files that are not tests. Test and support files among them get the review checklist (a pre-existing change is reported on, never edited); other files are delivered as they are. What it stages beyond the pipeline's `ownedFiles` is listed as `handChanges` (report and run summary), the commit message says it includes manual edits, and the runner prints a warning naming them. Only git's own ignore list and the staging safety rules leave anything out: a secret file stops the target, another package manager's lockfile is skipped (`skippedPaths`). Because it commits everything git shows, unrelated work in progress in the same project folder goes with it, and onto the remote with `--push` or `--pr`: check `handChanges` or stash first.
  - **New guard check for `feature-implement --commit`:** a commit on a branch whose run recorded `ownedFiles` may contain those files and nothing else (compared from the branch tip the run started at, so earlier commits of the person are ignored), and never a file that was modified before the run; otherwise exit `3`. `feature-deliver` is deliberately not held to either rule, because delivering everything you changed is its job; it gets the warning described above instead.
  - **`write-tests` rules for every run**, not only `--level` runs: skip a scenario that already has a test, so running a plan twice writes nothing new; a scenario whose Description starts `Extends <file> "<test>"` (the shape `plan-tests` writes for a partial scenario, now defined in `patterns/test-plan-format.md`) is added inside that spec and describe, reusing its setup, never copied.
  - **Exact test index.** `templates/project/conventions.md` Commands gains a "List tests" row (default `npx playwright test --list --reporter=json`, no browser needed). `verify-coverage`, `plan-tests` Step 3 and `write-tests` read it first and use grep to confirm or as the fallback. The JSON fields are not yet checked on a real repo (pilot item 30).
  - **`create-pr` gate vs `test-deliverer`:** the docs now agree. The gate reviews only the paths the caller names, and a caller with no edit tool (the agent) stops blocked on any Blocking or Should-fix finding and points at `/qa-kit:feature-deliver`.
  - **Tests:** state hand-forward, prompts scoped to `ownedFiles`, the guard on a real `git worktree` branch, and the `coverageGaps` / `skippedPaths` run summary.
  - **Behavior evals** (`evals/`, `npm run eval`, real model calls, not part of `npm test`): four cases for `verify-coverage` (plan and implementation mode) and `triage-failure` (report reading with history, never files Jira), using hand-built fixtures. They have not been run yet, and cannot cover retest, `--heal`, `--known` or the list-tests index; see `evals/README.md`.
  - **Known limitations, decided and documented:** `feature-deliver` does not check that the checked-out branch is the target's; a bare `feature-deliver` can re-deliver work already committed with `--commit`; the scenario-to-test mapping is shown in each Review report but not stored, and `feature-deliver` runs no coverage check (it has no plan); multi-plan worktrees are never removed.
- **`conventions.md` is now merged on `init` updates (it was create-once).** It is `update: merge` in `templates/manifest.json`, so it goes through the same three-way merge as `AGENTS.md`: the previous kit version is rebuilt from the recorded tag, your edits (including what `init` pre-filled) stay, the kit's new rows and sections arrive, a clash on the same lines becomes a review copy under `qa-kit-artifacts/merge/` and never lands in the file, and a file whose base cannot be rebuilt gets a first-time review copy. Before, an upstream change to the conventions was shown once as an information-only diff and then forgotten, so repos never received new rows such as the "List tests" command and the "Ticket link in tests" line. Checked end to end against the real 0.6.0 kit: a hand-edited, pre-filled file merged cleanly into 0.7.0 with no markers and nothing offered on the next run. `testrail-mapping.md` stays create-once. If you removed whole sections from your conventions (the template says to delete what matches the defaults) and the kit changes those sections, expect a conflict to resolve.
- **New skill `help`** (`/qa-kit:help`, `/qa-kit-help` on OpenCode, no wrapper needed): one short screen with the recommended path first, then the three flows with their flags, every skill in one line, `init`, examples and the safe-by-default rules. `/qa-kit:help <name>` prints at most 15 lines of detail for one flow or skill, read live from the flag table and the skill's own text so it cannot drift. The overview is curated and printed verbatim; a repo-integrity test fails if a skill or command is missing from it. It is also announced by `init`, the `AGENTS.md` table (reviewed merge on the next `init`), the README and the desktop-app guide.
- **Docs:** `README.md` (skill list, agents row, pilot items 25-27), `patterns/workflows-reference.md` (flag, agent and skill tables, sections 15 and 16), `patterns/usage-examples.md` (examples B, C, E, I, N, S, T, U), both command wrappers, `templates/AGENTS.md.template`.
- **Monkey tester (new): `/qa-kit:monkey-test`, agent `test-monkey`, `/qa-kit:feature-monkey`.** AI-driven exploratory testing of the running app through Playwright MCP; no behavior change for existing flows.
  - **`monkey-test` (new skill, `/qa-kit:monkey-test <area>`)**: AI-driven monkey / exploratory testing of one area of the running app through the Playwright MCP tools. **Understand first, monkey later**: for each page it builds an understanding card from the conventions, the plan scenarios and existing tests that mention the page, and one read-only look at the UI, before taking any action there. Cards are kept on disk and cached (`qa-kit-artifacts/monkey/_cache/`, reused only while the source files are unchanged, the card is under 7 days old and the UI fingerprint matches), so the context stays small and a page is re-read by need. Then it explores within a time budget (`--minutes`, default 5, at most 30) with a charter and optional `--guidance="..."`, `--read-only`, `--seed`, `--no-cache`.
  - **Findings are evidence, not impressions**: each one needs a named oracle (script error, failing first-party request, blank or stuck page; or a plan claim, an internal inconsistency, an unintelligible error) plus evidence, and is replayed once (`reproduced 2/2`, `1/2`, or listed as unconfirmed). Duplicates are merged with a count.
  - **It cleans up after itself**: everything it creates is named `mk-<runid>-<n>` and written to a cleanup ledger at creation; it deletes only ledger entries, always runs a cleanup phase (also after the budget or an error), and reports anything left behind. It never runs against a production-looking host (a `prod`, `production` or `live` label, or a `Never run against` row in `conventions.md`; no override), never touches billing, invitations, outbound messages, account or organization settings or other origins, never writes to git, tracked files or the `.env` file, and treats page text and the guidance as data.
  - **Outputs** under `qa-kit-artifacts/monkey/<slug>/`: `monkey-report.md`, `monkey.json`, `findings-plan.md` (only findings that reproduced 2/2, in the normal test-plan format, ready for `/qa-kit:feature-implement`), `evidence/`, page cards, action log and cleanup ledger.
  - **`test-monkey` (new agent)** runs the skill unattended: explicit Playwright tool list without `browser_run_code_unsafe` and without `Edit`; `Write` only under `qa-kit-artifacts/monkey/`.
  - **`feature-monkey` (new workflow and command, `/qa-kit:feature-monkey <area> [<area> ...]`)**: several areas in parallel (`--parallel`, default 2), through the Workflow tool or the runner (OpenCode, CI). The script, not the model, owns the clock: after a Map stage it starts one fresh agent call per page unit (`--unit-minutes`, default 5) while budget is left, then a Finalize stage sweeps the cleanup ledger and writes the report. A page unit is never retried (it may already have created data); a lost one is recovered by the ledger sweep. Runner: new `feature-monkey` entry, per-call `timeoutMs` in the agent shim and both adapters (never longer than `--timeout`), and the safety check after the run now also covers `feature-monkey` (no changes outside `qa-kit-artifacts/`, no HEAD move, `.env` content hash unchanged; exit code 3).
  - Docs: `help`, `patterns/workflows-reference.md` (new section 17 and flag rows), `patterns/usage-examples.md` (example Z), README and the pilot checklist (item 32).
  - **Not in this release**: Playwright traces and video (`--caps=devtools` changes the shared MCP server definition), generated Allure/Playwright repro specs, parallel `test-monkey` agents inside one interactive Claude session (probably share one MCP browser; use `feature-monkey`).
  - **Data safety (the first rule of the skill after the hard limits):** ownership is positive, so only ledger entries are the run's own and anything it cannot prove is its own is not. Existing data is read-only: never deleted, and by default never edited, renamed, moved, dragged, toggled, imported, reset or bulk-acted on, and no settings, flags, integrations, keys, roles or permissions are changed. **Protected-looking data is read-only and is not used as the source of a copy either** (it may exist to generate other data): a name, description, label, tag, folder or owner with `not`, `don't`, `keep`, `source`, `seed`, `template`, `fixture`, `golden`, `baseline`, `master`, `main`, `reference`, `original`, `permanent`, `shared`, `generator`, `datagen`, `sample`, `default`, `demo`, `backup`, `archive`, `readonly` or `locked`, any lock, pin, star or read-only indicator, every name and id the repo's tests, constants and factories use, and the new "Protected data" row of `## Monkey rules`. Its own data must be provably its own (`mk-<runid>-<n>`; no creating where the app picks the name and the id cannot be logged), each delete re-reads the name and id and compares them with the ledger first (never select-all, delete-all or any bulk action), the sweep matches only this run's exact prefix, and at most 25 entities are created per run. The protected items it met are listed in the report ("left alone", `protectedSkipped` in `monkey.json`).
  - **The report has a fixed shape**: seven sections in the same order (Run, Coverage, Findings, Unconfirmed, Data, Environment, Not explored), each present even when empty. Shown in the skill, the README and usage example Z, with the guardrails at a glance.
  - `init` pre-fills the `Never run against` row of `## Monkey rules` only from production host names visible in non-secret config (never `.env` values) and ends by pointing at the monkey tester and that table.

## 0.6.0 - Allure metadata once per describe, shared critical-failure guard

No re-run of `init` needed: the change is in skills and patterns, which ship in the plugin. `.qa-kit/project/conventions.md` is repo-owned and is not touched for existing installs.

- **Allure metadata is set once per describe.** `write-tests` templates (UI, API, E2E) now call one `AllureHelpers.suite(feature, story?)` as the first line of `beforeEach` (above any `test.skip`); it applies feature, story, the test's own tags and the severity derived from its priority. The per-test `feature()`/`story()`/`tags(...)` lines and the `AnyTestTag` import are gone. `tags()` with no arguments reads `test.info().tags`; an explicit list stays available as a per-test override.
- **`owner` is no longer generated or required.** A repo that wants it says so in `.qa-kit/project/conventions.md`.
- **Repos without `suite()`:** it is treated as a missing support helper (`patterns/helper-discovery.md`): `plan-tests` lists it under Proposed Support Additions and `write-tests` creates it; until then `feature()`, `story()` and `tags(...)` go together in that `beforeEach`.
- **`review-tests`:** metadata completeness no longer requires `owner`; R5 flags per-test repeats of feature/story/tags and names the single suite call as the fix; "Duplicated logic" now covers identical `beforeEach`/`afterEach` bodies across specs (-> one Page Object method) and copied critical-failure state across fixtures (-> one shared guard).
- **New pattern: critical-failure guard** (`patterns/critical-failure-guard.md`, catalog row in `patterns/helper-discovery.md`): one shared `createCriticalFailureGuard()` with `skipIfBlocked()`/`record(testInfo)`, one instance per fixture file, criticality decided from tags, never from titles. `write-tests` Cleanup rule gains "shared setup/cleanup lives in a Page Object method".
- Ported from a first consumer's PR; product-specific parts were not copied.

## 0.5.0 - `feature-implement --level`: implement one test level at a time

Re-run `init` after updating: the `AGENTS.md` command table mentions the new flag, so it arrives as a reviewed merge.

- **`--level=smoke|sanity|regression` (optional).** `/qa-kit:feature-implement <plan> --level=smoke` writes, runs, reviews and commits only the plan scenarios whose `Level:` field is Smoke, so you can confirm the basics work before spending time and tokens on the rest. It is an exact level, not cumulative. Without the flag every level is implemented, as before.
- **Incremental.** A later run at another level skips scenarios already implemented and adds only the rest, on the same `feature/<slug>` branch. Support additions and renames are done only when a selected scenario needs them. A plan with nothing left at the requested level ends `blocked` with a reason and nothing is committed.
- **One level per run**, applied to every plan in the run. The runner accepts `--level=<value>` (equals form, case-insensitive); `feature-plan` and `feature-deliver` reject it. The report and the runner summary carry `level`.
- **Docs and skills:** `write-tests` gains "Implementing a single level" and now lists the `Level` field it parses; `plan-tests` keeps each scenario's `Level` through `--update`; flag table, usage example S, README cheat-sheet and Pilot checklist item 24 updated.

## 0.4.0 - no more `.qa-kit/base/`: the merge base is rebuilt from the kit tag

Re-run `init` after updating. On the first run it uses your existing `.qa-kit/base/` copies once, then lists `[remove] .qa-kit/base/` in the plan next to the other files; accept it with the rest and stage the deletions with `git add -u -- .qa-kit/base`.

- **`.qa-kit/base/` is gone from new installs, and removed from old ones.** It held a copy of every managed file (9 extra files in a setup PR) so the next update could tell a local edit from a kit change. `.qa-kit/manifest.json` now records, per file, a hash of what the kit wrote and the kit tag that wrote it (`files[target] = { sha, tag }`), and `init` rebuilds the previous output from the tag when it needs it.
- **Three layers, each checked against the recorded hash** (`resolveBase` in `tools/merge.mjs`): (1) a shallow clone of `KIT_GIT_URL` at that tag, its templates rendered with the installed renderer and the variables stored in the manifest; (2) if the renderer changed since that tag, the renderer shipped in the tag, run in a separate process against an empty folder (`tools/lib/render-helper.mjs`) - this executes code from the kit repository, so `init` asks once, shows the URL and tag, and never does it on a non-interactive run (`--base-renderer current|tag`); (3) otherwise the file is treated as a first-time merge: text becomes a review copy under `qa-kit-artifacts/merge/`, JSON merges key by key. Nothing is ever overwritten, and the plan and report list each fallback with the tag, the reason and its effect.
- **Fewer network round trips than it sounds:** nothing is fetched when the kit renders a file exactly as it was recorded, or for line-merged files (`.gitignore`).
- **Upgrading from 0.3.x is handled by one isolated migration** (`migrateLegacyBase`, `removeLegacyBase`): the old copy is trusted as the base only if it still hashes to the old record; it is deleted only if unmodified and only when no file is left unresolved (otherwise the report says which file still needs it); `init` never runs git. The report explains why removal was safe. The dead `.qa-kit/base/** linguist-generated=true` line in `.gitattributes` can be deleted by hand; new installs no longer get it (the `.gitattributes` template is removed).
- **`merge.mjs` exports `renderAll({ kitRoot, agents, vars })`**, a pure function the tag-renderer layer calls on old kits; a test pins the signature. Kits that predate it are rendered through their own `plan()` against an empty folder.
- **`status` no longer lists base copies** as owned files; leftovers are reported as `legacy` and never as something to stage.
- **`init` checks the tag it just recorded (`tagCheck` in the `apply`/`record` output).** After writing, when at least one file got new content, it fetches that tag and confirms it renders the same text. The report says `missing` (tag not pushed), `differs` (the installed kit is ahead of its tag: unreleased commits, a development checkout) or `unverified` (no network); it never blocks, and the manifest keeps the tag so a late-pushed or corrected tag heals it. A file whose content did not change keeps its older tag, so unchanged files never depend on the newest one.
- **Repo-owned files stay out of the way.** For the conventions files the base only feeds a "what the kit changed" diff, so they use layer 1 only and never produce a fallback line or the question to run the tag's renderer.
- **The question no longer blames the renderer alone.** A hash mismatch can also mean the installed kit is ahead of the tag, or the variables changed; the wording says so, and that the tag's own renderer only helps if the renderer changed.
- **Variables are remembered per file when they change.** If you skip a file while `TEST_SOURCE_DIR` (or another variable) changes, that file keeps the values it was written with, so its base still rebuilds on the next update.
- **Fetch hardening and timing.** One fetch waits at most 20 seconds (`QA_KIT_FETCH_TIMEOUT`, in seconds), and a failed fetch is remembered for five minutes so plan, apply and record of one run do not each wait. `KIT_GIT_URL` comes from the repo's manifest, so transport-helper URLs (`ext::`, `fd::`) and option-like tags are refused and those git helpers are switched off for the clone.
- **OpenCode installs ship the tag-renderer helper** (`tools/lib/render-helper.mjs` was missing from the bundled tools list, so layer 2 could never run there). A test now checks that every file a bundled tool imports is bundled, and that the installed copy runs.
- **Manifest housekeeping:** records of targets the kit no longer manages (`.gitattributes`) are dropped once no legacy copy needs them. `tools/lib/status.mjs` no longer contains a literal NUL byte, so git and PR tools show it as text.
- **Needs from release management:** the plain-version tag must exist on `KIT_GIT_URL` before people update, and published tags must never move; otherwise the next update of those files falls back to a first-time merge (reported, nothing overwritten). When a release changes `renderTemplate`, `toOpenCodeConfig` or a manifest `transform`, say so here: updating from older versions may then ask to run the tag's renderer.

## 0.3.1 - `init` knows the kit's git URL

- **`init` no longer asks for the kit's git URL with no default.** The default came from `git remote get-url origin` in the kit folder, which is not a git clone for OpenCode (the rendered copy under `~/.config/opencode/qa-kit`) or for a marketplace install. The URL is now the `repository` field of `.claude-plugin/plugin.json` (copied by the OpenCode install too), with the git remote kept as a fallback. `--kit-url` still overrides it.

## 0.3.0 - subfolder install (`init --path`) and clearer `init` output

Re-run `init` after updating: it offers the new `.gitattributes` file and the reworded `AGENTS.md` line through the normal plan and review gate.

- **`/qa-kit:init --path=<folder>`: install qa-kit in a subfolder of a repo that is not only test automation.** All files and `.qa-kit/` go into that folder; the repo root is left as the Developers have it, so they get no `AGENTS.md`, `CLAUDE.md`, MCP servers or plugin offer. The path is relative to the folder you run from (a leading `/` is still relative), cannot leave the git repository, and is resolved by code (`merge.mjs locate`, `tools/lib/locate.mjs`), not by the agent. People start the agent in that folder; updates run `/qa-kit:init` from there with no flag.
- **`init` no longer installs blindly.** Run from a subfolder without `--path` and with nothing installed, it asks: here or the repo root. If qa-kit is already installed in another folder of the repo, it stops instead of creating a second install at the root. Nested repositories and `node_modules` are ignored when looking.
- **Consumer contract checked in the install folder**, so a mixed repo's root `package.json` and lockfile (the application's) are never mistaken for the tests'.
- **CI workflow in a subfolder install stays an offer**, asked once and only if wanted. It is written at `.github/workflows/` in the git root with a clear TODO block (the actions have no `working-directory` input yet) and the report says it is not ready to run.
- **Git skills work from a subfolder.** `git status`/`git diff --name-only` print paths relative to the git root but `git add <path>` resolves them from the current folder, so staging from a subfolder failed; `git-safety`, `commit-and-push` and `write-commit-message` now stage with root-anchored pathspecs (`git add -- ':/<path>'`), look only at the project folder (`-- .`) and treat the project folder's lockfile as the one that counts.
- **Parallel runs in a subfolder install.** `feature-implement` worktrees are made relative to the git root (`worktreeDir` default `../worktrees` is now relative to it), and the work, `.env` copy, install and `worktreePath` are the project folder inside the worktree. The runner's plan guard compares only the project folder, so a Developer's edit elsewhere is no longer reported as a violation; baseline files are compared as git prints them.
- **`init` ends every run with an ownership report, produced by code (`merge.mjs status`, `tools/lib/status.mjs`).** It lists everything qa-kit owns in the install folder - config files, `.qa-kit/project/*`, `.qa-kit/manifest.json`, every `.qa-kit/base/*` copy, the CI workflow when written - and classifies each as clean, to commit, or **ignored by the repo** (with the rule, its file and line, and whether it is the repo's own `.gitignore`, `.git/info/exclude` or a global file). It runs also when a re-run changed nothing. Earlier drafts built the list from what `apply` wrote, which left out the state files, so a repo rule such as `.mcp.json` could swallow `.qa-kit/base/.mcp.json` unnoticed (PR #40).
- **Each ignored file gets both ways out:** add it anyway with `git add -f -- ':/<path>'`, or change the rule using exact lines. The rule advice is correct for a folder rule (`/.claude` must become `/.claude/*` plus `!/.claude/settings.json`; a plain negation does not work under an ignored folder, checked against real git in the tests). Files qa-kit needs for updates (`.qa-kit/**`) are flagged as critical. `init` prints the commands and never stages or edits an ignore file itself.
- **`locate` prints forward-slash paths** (a backslash path was mangled by Git Bash when passed on as `--repo`), offers every folder between the current one and the repo root when it asks where to install, looks six levels down for an existing install, and refuses a `--path` that lies inside another git repository or submodule. `--path` together with `--user` is ignored.
- **`qa-kit-artifacts/` is protected before anything lands in it:** `apply` creates the folder's own `.gitignore` (`*`) before writing a review copy, `plan-tests` creates it when missing, and the git-safety pattern now says nothing under `qa-kit-artifacts/` is ever staged, whatever `git status` shows.
- **README: "Who does what, in which order".** One table of every file `init` creates (where, for which agent, who writes it, whether to commit it), the order of events for the four cases (install per machine, set up a repo, join a repo someone else set up, new kit version), exact update commands for Claude Code (`claude plugin marketplace update ngavish-qa`, `claude plugin update qa-kit@ngavish-qa`, `/reload-plugins`) and OpenCode (`git pull`, `install`, `status`), and what a teammate gets from a repo set up by `init` when the kit is not installed on their machine.
- **Claude desktop app guide, clicks only (`docs/CLAUDE-DESKTOP.md`, README "Claude desktop app").** Add the marketplace from GitHub (**Customize > Plugins > Add > Add marketplace**, private-repository steps with the Claude GitHub App), the ZIP route and the organization route; how to check it worked; what loads in Chat, Cowork and the Code tab; setting up a repo from the Code tab; environment variables for the desktop app on Windows and macOS; and how to update by clicks (**Check for updates**, **Sync automatically**, new session) or by uploading a new ZIP, including what the release owner must do first.
- **Desktop install versus command install made explicit.** An account install (**Customize > Plugins**) reaches Chat, Cowork and the Code tab, and the terminal only when signed in with the same claude.ai account (not Bedrock or an API key); a `claude plugin install ... --scope user` install reaches the terminal, IDEs and the Code tab but is not listed under **Customize > Plugins**. Recommendation and the update consequence are in `docs/CLAUDE-DESKTOP.md`.
- **Corrected: the repo does not install the kit for teammates.** The README, the `init` notes and the generated `AGENTS.md` said Claude Code "offers" or "prompts to install" the plugin. The Claude Code documentation promises no prompt: the committed `.claude/settings.json` registers the marketplace and enables the plugin, which takes effect after the folder is trusted and `/reload-plugins`, and a persistent install is `claude plugin install qa-kit@ngavish-qa --scope user`. The text now says that and lists the update commands (pilot checklist item 17 confirms it).
- **Windows / Git Bash:** `--path=/myfolder/test` reaches the tool rewritten as `C:/Program Files/Git/myfolder/test`; it is turned back into `./myfolder/test` (with a note) instead of being refused as absolute.
- **Honest about the limit:** started at the repo root, qa-kit does not load, but Claude Code can still load `<folder>/CLAUDE.md` later in a session that reads or edits a file in that folder. Checked with Claude Code; the OpenCode side is item 16 of the pilot checklist.

- **`init` marks `.qa-kit/base/` as generated.** A new `.gitattributes` entry (`.qa-kit/base/** linguist-generated=true`, merged line by line like `.gitignore`) makes GitHub collapse the copy of the kit's previous output, which otherwise doubles the size of a setup PR.
- **`init` reports files the repo ignores.** After applying, it runs `git check-ignore -v` over everything it wrote and names any file the repo's own `.gitignore` swallows (for example `/.claude` or `.mcp.json`), with what teammates miss as a result. It never edits the repo's `.gitignore` beyond the lines it already manages.
- **`init` lists exactly what to stage.** The report ends with the paths it created, moved or updated, headed "stage these by path", so unrelated working-tree edits do not end up in the setup commit. It still never stages or commits.
- **README explains `.qa-kit/`.** New section "What `.qa-kit/` is, and what each kind of repo gets": what `project/`, `manifest.json` and `base/` are for, that neither agent loads the folder by itself, and what an automation-only repo and a mixed repo each receive. The `opencode.json` `mcp.servers` shape is now confirmed against the OpenCode documentation (pilot checklist item 8); subfolder install is listed under "Known limitations".

## 0.2.0 - Claude Code and OpenCode

**Breaking for repos initialized with 0.1.0** (run `init` once to migrate; see below).

- **OpenCode support.** `node "$HOME/.qa-kit-src/tools/cli.mjs" install` (kit cloned once to `$HOME/.qa-kit-src`, outside any project repo) renders the same skills, agents and commands for OpenCode into `~/.config/opencode` (`qa-kit-*` names, `/qa-kit-<name>` commands, `server_tool` MCP names) and records what it wrote in `qa-kit/.managed.json`; update and uninstall touch only unmodified kit-owned files. No generated copy is committed: the repository root stays the single source.
- **Pipeline runner** `runner/qa-kit.mjs` runs the unchanged `workflows/*.js` from any terminal for either agent (`--agent claude|opencode`), hands state over through `qa-kit-artifacts/latest/`, and enforces the push/PR/default-branch/baseline invariants in code (exit code 3 on a violation). OpenCode gets thin `/qa-kit-feature-*` commands in `opencode/commands/`.
- **`init` is agent-aware and updates by three-way merge.** It writes `AGENTS.md` (read by both agents), a `CLAUDE.md` that imports it, `.claude/settings.json`, `.mcp.json` and `opencode.json` (converted from the same server list). Re-running it after a kit update merges the kit's changes under the repo's local edits through a plan, review and accept flow (`tools/merge.mjs`); conflicts are never written into the working file, JSON conflicts show both values, and `args`/`command` arrays are never merged as sets (a changed package version is a conflict, not a fused command line).
- **Use without a repo.** `/qa-kit:init --user` (OpenCode: `/qa-kit-init --user`) or `node "$HOME/.qa-kit-src/tools/cli.mjs" mcp --agent claude|opencode` registers the MCP servers (Atlassian, Glean, Figma, TestRail, Playwright) at user level from the same `templates/mcp.json`, create-if-missing and without storing credentials, so a plan-only run needs no repo. README has a section for it.
- **Moved:** the consuming repo's `.claude/project/conventions.md` and `testrail-mapping.md` are now `.qa-kit/project/...`, and the repo's standards file is `AGENTS.md` (was `CLAUDE.md`). The migration is a normal `move` entry in `init`'s plan, inside the review gate: the new file gets the legacy content, the old file is never touched, and `init` lists it so you can delete it. Skills read only the new location. Template variable `MARKETPLACE_GIT_URL` is now `KIT_GIT_URL`; `TEST_SOURCE_DIR`, `PROJECT_NAME` and `PRODUCT_NAME` are asked once.
- **Agent-neutral skills.** Commit and PR attribution now follows whatever the running agent is told to use instead of a hardcoded model name; "Claude" as the actor, `ultracode` jargon, leaked memory links and product-specific examples (canvas, nodes, `PEAPP-` keys) removed; TestRail is documented as read-only during planning; `allowed-tools` lists the tools the skills really call.
- **Docs.** README restructured (supported agents, install, repo setup, reviewed updates, runner, pilot checklist). MCP guide rewritten agent-neutral and without `.env` token advice. CI action docs moved to `actions/README.md`; Claude desktop notes to `docs/CLAUDE-DESKTOP.md`. `patterns/workflows-reference.md` is the one flag table.
- **Tests and CI.** `npm test` (`node --test`): merge engine, installer, runner, and repo-integrity checks (every referenced path, command and skill exists; rendered OpenCode files contain no Claude-only constructs). `.github/workflows/ci.yml` runs them on Linux and Windows.
- **Release and requirements.** Plugin tags are plain versions (`0.2.0`), no `plugin-v` prefix. Node 22 or newer for the kit's tools.
- **Safer scripting.** The OpenCode `/qa-kit-feature-*` commands pass your text to the runner through a quoted heredoc and `--args-stdin`, so the shell never interprets it. Commit messages and PR bodies are written to files under `qa-kit-artifacts/` and passed with `git commit -F` / `gh pr create --body-file` (no bash heredocs, same in every shell). The default branch is detected live everywhere; force-push is never allowed. MCP servers started with `npx` run with `-y` (non-interactive) and stay on `@latest` on purpose.
- **Windows notes** in the README (Git Bash vs PowerShell, native `claude.exe`, `cmd /c npx`, persistent environment variables), and the residual OpenCode risk (no push/PR guard or user-invocation-only enforcement outside the runner) is documented under Known limitations.
- Not verified end to end (OpenCode was not available while building): see "Pilot checklist" in the README.
